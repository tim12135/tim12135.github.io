SaaS 多租户差异化表单设计方案总结

一、问题背景

在 SaaS 场景中，不同租户（客户）虽然共享同一套业务系统，但往往需要根据自身业务特点自定义表单字段。例如：

  • 租户 A 的 CRM 需要记录”客户行业分类”字段
  • 租户 B 的 CRM 需要记录”客户信用等级”字段
  • 租户 C 需要在标准字段基础上额外增加 20 个自定义字段

核心挑战在于：如何在共享底层数据结构的前提下，让每个租户拥有独立的字段配置（Field Definition）和数据存储（Field Value），同时保持查询性能、数据一致性和可维护性。

二、主流数据结构设计方案

方案一：EAV 模型（Entity-Attribute-Value）

数据结构

每条业务数据的一个自定义字段值占一行，通过 field_id 关联到字段定义。

优点

  • 架构简单直观，扩展性强，新增字段无需改表结构
  • 支持行级并发锁，不同字段更新互不干扰
  • 删除字段只需清理元数据 + 级联删除值行
  • 对关系型数据库友好，不依赖特定数据库特性

缺点

  • 查询一个实体的所有字段需要大量 JOIN 或多次查询，性能差
  • 无法利用数据库的类型约束，所有值以字符串存储
  • 复杂条件查询（多字段组合过滤）SQL 极其冗长且低效
  • 存储膨胀严重，每条数据的每个字段值都占独立行，标识符重复存储
  • 写入性能随索引数量增长而下降

适用场景

  • 自定义字段数量较少（< 50）
  • 传统成熟系统的局部字段扩展
  • 对查询性能要求不高的轻量级配置场景

方案二：JSON / JSONB 列存储

数据结构

所有自定义字段值打包成一个 JSON 存储在主表的一个列中，字段定义表仅作为元数据描述。

优点

  • 存储紧凑，一条数据一行，无冗余行
  • 读写性能好，一次 IO 即可获取全部字段
  • PostgreSQL 的 JSONB 支持 GIN 索引，可对 JSON 内部键值高效查询
  • 字段数量无上限，天然支持嵌套结构
  • 开发简单，ORM 友好

缺点

  • 行级锁导致并发更新同一记录的不同字段时产生写争用
  • 全局字段删除需要遍历所有行清理 JSON 中的对应键
  • 无法强制严格的数据类型约束（依赖应用层校验）
  • 深层嵌套查询复杂度随层级增长
  • 部分传统关系型数据库（如 MySQL 5.7 以下）JSON 支持有限

适用场景

  • 大多数可扩展的 SaaS 产品（推荐首选方案）
  • 字段数量多但单条数据并发更新不频繁
  • 使用 PostgreSQL / MongoDB 等对 JSON 原生支持好的数据库
  • 需要快速迭代的敏捷型产品

方案三：宽表模式（预留列 / Flex Columns）

数据结构

预先在主表中创建固定数量的预留列（如 val_00 ~ val_99），通过元数据表记录每个租户的字段映射到哪个预留列。Salesforce 即采用此方案的核心变体。

Salesforce 的实践

Salesforce 的多租户架构基于”Universal Data Dictionary (UDD)”：

  • 每条数据通过 OrgID 隔离租户
  • flex columns 以”canonical format”（规范字符串格式）存储所有类型数据
  • 运行时引擎根据 MT_Fields 的类型定义做类型转换
  • 通过大规模元数据缓存 + 按 OrgID 物理分区裁剪提升性能

Salesforce Flex Columns 技术细节

1. MT_Data 表的列类型与长度

字段类型：所有 Value 列均为变长字符串（VARCHAR / VARCHAR2）

  • 无论业务字段是数字、日期、文本还是布尔，底层统一存储为字符串
  • 数据库层面不区分类型，所有类型约束和校验在应用层完成
  • 每行的 501 个 Value 槽位对应 Salesforce 每个对象最多约 500 个自定义字段的限制

长度设定策略：

数据类型 存储方式 长度处理
文本（Text） 直接存入 Value 列 最长 255 字符存入 flex column
长文本（Long Text Area） 外置到 MT_Clobs 表 最长 32,000 字符，CLOB 存储
数字（Number） 转为规范字符串存入 Value 列 如 12345.67 → "12345.67"
日期/时间（Date/DateTime） 转为规范字符串存入 Value 列 如 2026-07-16 → "2026-07-16T00:00:00Z"
布尔（Checkbox） 转为字符串 "true" / "false"
选项列表（Picklist） 直接存入 Value 列 存储选项的 API Name 字符串
关系（Lookup/Master-Detail） 存储目标记录 ID 18 位或 15 位 ID 字符串

关键设计：长短分离

  • 短数据（≤ 255 字符）→ 存入 MT_Data 的 flex column（VARCHAR）
  • 长数据（> 255 字符，最长 32,000）→ 存入 MT_Clobs 表（CLOB 类型），主表只保留引用

MT_Clobs 表结构（一个记录有多个长文本字段怎么存？）：

MT_Clobs 采用与 MT_Indexes 相同的”一行一个字段值”模式。一条业务记录上有 N 个长文本字段，就在 MT_Clobs 中产生 N 行，通过 FieldID 区分：

  • 同一条记录（RecordID=1001）有 3 个长文本字段（FieldID=10/11/12），占 3 行
  • 每行只存一个 CLOB 值，通过 (OrgID, ObjectID, RecordID, FieldID) 四元组唯一定位
  • MT_Data 中对应的 Value 列存一个简短引用标记（如字段 ID 或 null），表示”该字段值在 MT_Clobs 中”

为什么不用一行存多个 CLOB 列？（如 ClobValue0 ~ ClobValueN）

方案 一行一个 CLOB（实际方案） 一行多个 CLOB 列
扩展性 无限，新增长文本字段无需改表 有上限，需预留列
行大小 每行只有一个 CLOB，行大小可控 多个 CLOB 堆在一行，行可能超大
更新性能 更新单个字段只锁一行 更新任一字段锁整行
存储效率 为空的 CLOB 不占行 空列仍占位
查询方式 按 FieldID 过滤 需知道列位置

这与 MT_Indexes 的设计思路完全一致：用行数换列数，牺牲少量 JOIN 性能换取无限扩展性。

3. MT_Fields 元数据表结构
  • FieldNum：核心映射字段，指定该自定义字段的数据存储在 MT_Data 的哪个 Value 槽位
  • 同一个 Object 下，每个租户的 FieldNum 独立编号（不同租户可复用同一个 Value 列）
  • DataType：记录原始业务类型，供运行时做类型转换
  • IsIndexed：标记该字段是否需要索引，决定是否同步写入 MT_Indexes
4. MT_Indexes 索引透视表

由于多个不同类型的业务字段共享同一个 VARCHAR Value 列，数据库原生索引无法有效工作。Salesforce 引入了 MT_Indexes 透视表：

RecordID 是最关键的列——它指向 MT_Data 中的 ObjectInstanceID，是连接索引与原始数据的桥梁。

为什么需要 MT_Indexes（核心问题解答）：

如果不加 MT_Indexes，在 MT_Data 上直接查询 WHERE Value1 > 5000000 面临两个致命问题：

  1. 类型错误：Value1 是 VARCHAR 列，存的 "5000000" 是字符串。字符串比较 "5000000" > "4999999" 的结果在数据库层面是不可靠的（字符串按字典序比较，"5000000" < "4999999" 为 true，因为字符 '5' > '4' 但长度不同会导致错乱）。更严重的是 "10000000" < "5000000" 在字符串比较下成立（因为 '1' < '5'），完全错误。

  2. 语义混淆：同一个 Value1 列，租户 A 存的是数字 revenue，租户 B 存的可能是文本 credit_level。如果直接在 Value1 上建索引，索引中混合了数字字符串和文本字符串，查询结果毫无意义。

MT_Indexes 通过以下设计解决了这两个问题：

  • 强类型列（NumValue/DateValue/StringValue）：让数据库以正确的数据类型做比较和索引
  • FieldID 过滤：确保只比较同一语义的字段值，不会跨租户、跨字段混淆
  • RecordID 回表：拿到匹配的 RecordID 后，回到 MT_Data 取完整记录

本质是”二级索引”模式：MT_Data 是堆表（主存储），MT_Indexes 是二级索引表。写入时同步写两处（主表 + 索引表），读取时先查索引表拿 ID，再回表取数据——这与数据库内部 B-Tree 二级索引的工作原理完全一致，只是 Salesforce 在应用层手动实现了它。

5. 整体数据读写流程

写入时：MT_Fields 决定数据写入哪个 Value 列、是否同步 MT_Indexes、是否外置 MT_Clobs
读取时：MT_Fields 决定从哪个 Value 列读取、用何种类型转换函数还原

6. 关键设计总结
设计点 方案 原因
列数据类型 统一 VARCHAR（变长字符串） 避免为每种业务类型建列，实现统一存储
列数量 501 个（Value0Value500） 平衡单行存储容量与字段扩展需求
短数据长度 ≤ 255 字符存入 flex column 控制 VARCHAR 列的物理存储大小
长数据长度 ≤ 32,000 字符存入 MT_Clobs 超长数据不撑大主行，外置 CLOB
类型处理 canonical format + 运行时转换 数据库不负责类型安全，应用层全权处理
索引策略 MT_Indexes 透视表 + 强类型列 解决 VARCHAR 列无法按原始类型索引的问题
元数据驱动 MT_Fields 的 FieldNum 映射 新增字段只需插元数据行，零 DDL
7. 查询引擎中间层（开发者怎么查 MT_Data？）

开发者绝不直接写 SQL 查 MT_Data。 Salesforce 在应用层和数据库之间构建了一个完整的运行时查询引擎，开发者只需写 SOQL（Salesforce Object Query Language），引擎自动完成从逻辑字段到物理列的翻译。

元数据缓存：引擎高效的关键

如果没有缓存，每次查询都要先查 MT_Fields 获取字段映射，再查 MT_Data 取数据——两次数据库往返。Salesforce 的解决方案：

  • 每个 App 节点维护一份分布式内存元数据缓存
  • 字段定义变更时，缓存自动失效并重新加载
  • 缓存命中率极高（字段定义变更频率远低于数据读写频率）
  • 效果：SOQL → SQL 翻译在内存中完成，零额外数据库查询
总结：三层架构职责划分

业务端绝不会自己拼接 SQL。 整个翻译过程由运行时引擎 black-box 完成——这就是 Salesforce “元数据驱动架构”的核心价值：开发者面对的是逻辑对象模型，引擎负责一切物理映射。

8. 联表查询（SOQL Relationship Queries）

支持，但方式和 SQL JOIN 完全不同。 SOQL 没有 INNER JOIN / LEFT JOIN 关键字，不支持任意表之间的自由关联。只能通过预定义的关系（Lookup / Master-Detail）进行导航式查询。

① 子查父（Child-to-Parent，向上导航）

② 父查子（Parent-to-Child，向下导航）

用子查询（嵌套 SELECT）获取子记录列表，最多 1 级：

等价 SQL 语义：Account LEFT JOIN Contact ON Contact.AccountId = Account.Id

常见 SQL JOIN 的 SOQL 等价写法
SQL JOIN 类型 SOQL 等价写法 示例
LEFT JOIN（父→子） 子查询 SELECT Name, (SELECT Name FROM Contacts) FROM Account
LEFT JOIN（子→父） 点号语法 SELECT Name, Account.Name FROM Contact
INNER JOIN（子→父） 点号 + WHERE 过滤 SELECT Name, Account.Name FROM Contact WHERE AccountId != null
INNER JOIN（父→子） 半连接子查询 SELECT Name FROM Account WHERE Id IN (SELECT AccountId FROM Contact)
LEFT ANTI JOIN NOT IN 子查询 SELECT Name FROM Account WHERE Id NOT IN (SELECT AccountId FROM Contact)
与 SQL JOIN 的核心差异
维度 SQL JOIN SOQL Relationship Query
关联条件 任意字段（ON A.col = B.col） 只能用预定义关系字段（Lookup / Master-Detail）
JOIN 关键字 INNER JOIN / LEFT JOIN / RIGHT JOIN 无关键字，用点号或子查询
任意表关联 支持（任意两表只要有逻辑关联即可 JOIN） 不支持（必须有预定义关系）
向上深度 无限制 最多 5 级
向下深度 无限制 最多 1 级子查询
多对多 通过中间表 JOIN 需通过 junction object 分两步查
聚合 + JOIN 自由组合 受限（子查询中不能有聚合）

关键点：Account 和 Contact 在物理层共享同一张 MT_Data 表，只是 ObjectID 不同。关系查询本质是 MT_Data 自连接（Self-Join）。

如果是父查子（带子查询），引擎翻译为不同的策略：

为什么父查子用两步而非一个 JOIN？

策略 一个 JOIN 两步查询（实际方案）
SQL 复杂度 一条复杂 SQL 两条简单 SQL
结果集 笛卡尔积（父行 × 子行），需应用层去重 父记录一组 + 子记录一组，天然分组
结果结构 扁平行（需要应用层组装成嵌套结构） 直接映射为嵌套 JSON
数据库压力 一条大 JOIN（自连接 + 可能的索引扫描） 两条简单查询（各走各自索引）
分页友好 难（子记录数膨胀导致分页不准） 易（父记录分页，子记录各自独立）

Salesforce 选择两步查询策略，因为 SOQL 的返回结构本身就是嵌套的（Account 里嵌套 Contacts 数组），两步查询的结果天然就是嵌套结构，无需应用层组装。

优点

  • 单行存储，读取性能优于 EAV
  • 规避了表结构变更（DDL）风险
  • 保持了关系型表结构，可做有限 SQL 查询
  • 适合大规模多租户 SaaS，Salesforce 已验证可行性

缺点

  • 预留列数量有上限，超出后需 DDL 扩列
  • 所有值以字符串存储，类型转换在应用层完成
  • SQL 查询能力受限，复杂查询需应用层拼装
  • 多租户共用列，索引策略复杂，不同租户的同一列语义不同
  • 开发成本极高，需要构建完整的元数据引擎和运行时
  • 数据库账号权限管理不当易引发跨租户数据越权

适用场景

  • 超大规模多租户 SaaS 平台（如 Salesforce 级别）
  • 垂直领域 SaaS，字段模式相对固定
  • 团队有强基础设施能力，可投入大量研发资源

方案四：动态 DDL（运行时修改表结构）

数据结构

每个租户有独立的表或独立的列，通过 DDL 在运行时动态创建/修改：

或采用每租户独立表（Table-per-Tenant）策略。

优点

  • 完全的关系型能力：类型约束、索引、复杂 SQL 查询全部原生支持
  • 数据一致性强，可利用外键、CHECK 约束
  • 对外部 BI 工具和报表系统友好
  • 无需额外的元数据引擎，直接读取数据库 Schema

缺点

  • 需要 DBA 级别权限，安全风险高
  • DDL 操作（ALTER TABLE）在高并发下可能引发锁表
  • 多数据库方言适配成本高（MySQL / PostgreSQL / Oracle DDL 语法不同）
  • 表数量随租户增长膨胀，元数据管理困难
  • 字段重命名 / 删除时数据迁移成本高
  • 不适合 Serverless / 云原生无状态部署

适用场景

  • ERP、MES 等企业级复杂系统（国内主流选择）
  • 租户数量有限且稳定的私有化部署场景
  • 对数据一致性和 SQL 查询能力要求极高的系统

方案五：混合方案（Hybrid）

实际生产中，成熟产品往往采用组合策略：

常见组合模式

组合 标准字段 自定义字段 代表产品
关系列 + JSON 固定列存储 JSON 列存储 大多数现代 SaaS
关系列 + EAV 固定列存储 EAV 行存储 传统企业系统
元数据引擎 + Flex Columns 元数据定义 flex 列存储 Salesforce
关系列 + 文档库 核心表存储 MongoDB 扩展 中大型 SaaS

典型实践：标准字段用关系列 + 自定义字段用 JSON

  • 标准字段享受关系型全部优势（索引、约束、查询优化）
  • 自定义字段享受 JSON 灵活性
  • 高频查询的自定义字段可通过表达式索引提升性能
  • 字段定义表驱动前端表单渲染和数据校验

  • 核心表：MT_Objects（对象定义）、MT_Fields（字段定义）、MT_Data（数据存储）
  • 关键设计：UDD 统一数据字典 + 元数据缓存 + 按 OrgID 物理分区裁剪
  • 亮点：将所有类型数据统一为 canonical format 字符串存储，运行时类型转换

Form.io

  • 方案：Schema-Driven（JSON Schema）
  • 核心设计：表单定义和提交数据均为 JSON 结构，分离存储
  • 多租户：通过资源定义、权限控制、认证隔离实现租户定制
  • 亮点：表单 JSON Schema 即是前端渲染蓝图，也是数据校验规则，做到”配置即代码”

钉钉宜搭 / 飞书低代码

  • 方案：模型驱动的混合方案
  • 核心设计：标准字段关系列 + 自定义字段扩展存储
  • 亮点：可视化表单设计器直接映射到后端数据模型，零代码创建租户专属表单

传统 ERP / MES

  • 方案：动态 DDL
  • 核心设计：每租户独立表结构，运行时 ALTER TABLE
  • 亮点：完全关系型能力，适合复杂业务约束场景

五、选型建议

按产品阶段选型

阶段 推荐方案 理由
MVP / 早期 JSON/JSONB 开发快、迭代灵活、PostgreSQL 原生支持
成长期 混合方案（标准列 + JSON） 兼顾性能与灵活性
成熟期 评估是否需要宽表/元数据引擎 当 JSON 性能瓶颈出现时演进

按业务特征选型

业务特征 推荐方案
字段数量 < 30，查询简单 JSON/JSONB
字段数量 > 100，需复杂查询 混合方案 + 表达式索引
需要 BI/报表对接 动态 DDL 或 混合方案（标准字段关系列）
超大规模 SaaS（万级租户） 宽表 + 元数据引擎
私有化部署、租户少 动态 DDL
需要嵌套/层级数据 JSON/JSONB

通用架构原则

  1. 元数据与数据分离：无论哪种存储方案，字段定义（元数据）必须独立于字段值（业务数据）
  2. 租户隔离优先：所有表必须带 tenant_id，所有查询必须强制过滤
  3. 标准 + 扩展分层：高频通用字段用关系列，低频定制字段用扩展存储
  4. 索引策略前置：在设计阶段就规划好哪些自定义字段需要索引，避免后期补救
  5. 数据校验在应用层：JSON / EAV / 宽表方案均无法依赖数据库做类型约束，需在应用层构建校验引擎

六、总结

没有”最好”的方案，只有”最合适”的方案。核心权衡轴是 灵活性 vs 性能 vs 复杂度：

  • 追求极致灵活 + 快速迭代 → JSON/JSONB（中小型 SaaS 首选）
  • 追求关系型能力 + 数据一致性 → 动态 DDL（企业级私有部署）
  • 追求超大规模 + 多租户隔离 → 宽表 + 元数据引擎（Salesforce 路线）
  • 追求平衡 → 混合方案（标准关系列 + JSON 扩展列，多数成熟 SaaS 的选择）

原因分析

直接原因：FTP 使用了主动模式（PORT），数据通道建立失败

日志中出现了 PORT 10,221,8,11,158,135 命令，这是主动模式的标志。其含义是：

  • 客户端告诉 FTP 服务器：”请向 10.221.8.11:40583（158×256+135）发起 TCP 连接来建立数据通道”
  • 服务器回复 200 PORT command successful，随后发送 150 Opening ASCII mode data connection
  • 但服务器实际回连客户端内网地址 10.221.8.11 时，由于 NAT/防火墙的原因，该地址对服务器不可达
  • 数据通道始终无法建立，listFiles() 无限等待

根本原因：代码默认未启用被动模式，也未设置任何超时

  1. FtpsWrapper.configureClient() 从未调用 enterLocalPassiveMode()，Apache Commons Net 默认使用主动模式。

  2. FtpsFileResourceServiceImpl.downloadFiles() 中有被动模式开关：

    但 FileResourceConfig.ftpLocalPassiveMode 的数据库默认值为 false，被动模式未被启用。

  3. 未设置任何超时——实际连接使用的 FTPClient 没有设置 setConnectTimeout、setDefaultTimeout、setDataTimeout，数据通道连不上时无限阻塞，不会报错也不会超时。

主动模式 vs 被动模式

主动模式（PORT） 被动模式（PASV）
数据通道建立 服务器主动连接客户端 客户端主动连接服务器
日志特征 PORT 命令 PASV 命令
NAT/防火墙 需服务器能回连客户端内网，通常失败 客户端主动出连，通常可通
适用场景 客户端有公网IP 现代网络环境（推荐默认）

解决方案

在 FtpsWrapper.configureClient() 中统一设置被动模式和超时：

各超时说明

方法 作用 说明
setConnectTimeout(30000) 连接 FTP 服务器超时 30秒内连不上则报错
setDefaultTimeout(60000) 控制通道（命令）读取超时 60秒内收不到服务器响应则报错
setDataTimeout(60000) 数据通道（LIST/RETR等）读取超时 60秒内数据通道无数据读取则报错，防止无限挂起

注意：setDataTimeout 设置的是 socket 的 SO_TIMEOUT，即两次数据读取之间的最大间隔，不是总传输时间限制。大文件下载只要数据持续流式传输就不会被中断，只有网络卡死或断开时才会触发超时。

unicode与UTF的计算逻辑

发表于 2025-11-13 分类于 算法 Valine：

unicode 码位，是对应字符的一个逻辑坐标。而真正用于存储到磁盘上的时候，会转换成特定的字符集，如 UTF-16、UTF-8、UTF-32 等。

UTF-16

UTF-16 一般一个字符占用 16 位或者 32 位，即 2 个字节或者 4 个字节。

unicode 码位大于 0xFFFF 时，此时需要减去 0x10000，然后拆分成高 10 位和低 10 位。
高位加上 0xD800，低位加上 0xDC00，然后转换成 UTF-16。

如：字符 𝒙，对应 unicode 码位是 U+1D499。

UTF-8

UTF-8 是一种可变长度编码，一般一个字符占用 1~4 个字节。

Unicode 码位范围 UTF-8 字节数 编码格式（二进制模板）
U+0000–U+007F 1 0xxxxxxx
U+0080–U+07FF 2 110xxxxx 10xxxxxx
U+0800–U+FFFF 3 1110xxxx 10xxxxxx 10xxxxxx
U+10000–U+10FFFF 4 11110xxx 10xxxxxx 10xxxxxx 10xxxxxx

如：字符 𝒙，对应 unicode 码位是 U+1D499。

UTF-32

UTF-32 一个字符固定占用 4 个字节。unicode 码位通过补零扩成 32 位，然后按端序摆字节即可。

如：字符 𝒙，对应 unicode 码位是 U+1D499。

BOM

BOM 是 Byte Order Mark 的缩写，中文常叫“字节顺序标记”。

它不是一个“可见字符”，而是一个特殊的 Unicode 码位 U+FEFF（Zero-Width No-Break Space），放在文本文件最开头，用来告诉程序：
“这份文件用的是哪种 Unicode 编码、哪种字节序。”

常见 BOM 字节序列：

编码名称 BOM 十六进制 字节序含义
UTF-8 EF BB BF 只是声明“我是 UTF-8”，不涉字节序
UTF-16 LE FF FE 小端序（Little-Endian）
UTF-16 BE FE FF 大端序（Big-Endian）
UTF-32 LE FF FE 00 00 32 位小端
UTF-32 BE 00 00 FE FF 32 位大端

UTF16 必须在开头放上 BOM（FE FF 表示 BE，FF FE 表示 LE），否则字节序未知。Windows 系统内部默认使用 UTF-16 LE。

Mysql数据隔离和MVCC

发表于 2024-09-10 更新于 2024-09-11 分类于 Mysql Valine：

并发事务所产生的问题

  1. 脏读
    读到了其他事务未提交的数据。未提交意味着这些数据可能会回滚，读到了不一定最终存在的数据，这就是脏读。
  2. 不可重复读
    在一个事务内，最开始读到的数据和事务结束前任意时刻读到的同一批数据出现不一致的情况。
  3. 幻读
    在一个事务内，相同的查询条件不同时刻读到的结果数量不一致。

隔离级别

  1. 读未提交 READ UNCOMMITTED
    允许事务读取未被其他事务提交的变更。可能会导致脏读、不可重复读、幻读。
  2. 读已提交 READ COMMITTED
    只允许事务读取已经被其他事务提交的变更。可以避免脏读，但可能会导致不可能重复读、幻读。
  3. 可重复读 REPEATABLE READ
    确保事务可以多次从一次字段读取相同的值，在这个事务持续期间，禁止其他事务更新这个字段。可以避免脏读和不可重复读，但可能导致幻读。
  4. 序列化 SERIALIZABLE
    提供严格的事务隔离。事务串行化顺序运行，可以避免所有并发问题，但性能最差。

Mysql 默认隔离级别：REPEATABLE READ，可以通过语句select @@tx_isolation;查询。

MVCC

MVCC 全称 Multi-Version Concurrency Control，即多版本并发控制。其目的是为了尽量避免并发事务读写场景下的上锁。

隐藏列

DB_TRX_ID：更改当前记录的事务 id
DB_ROLL_PTR：回滚指针，指向 undo log 的指针
DB_ROW_ID：innodb 为没有主键和唯一索引的表自动添加的隐藏主键

快照读和当前读

  • 快照读：普通的 select 查询语句（不加锁的 select）就是快照读，快照读是基于 MVCC
  • 当前读：执行 insert、update、delete 以及 select … for update、select … lock in share mode 时，会读取最新版本数据

Undo Log

Undo Log 的目的：

  • 确保事务的原子性。即如果需要回滚，则可以根据 UndoLog 来撤销之前未提交的数据变更。
  • 实现 MVCC。Undo Log 记录了反向操作记录，可得出之前版本的数据，作为数据的旧版本快照，并形成了一条数据版本链，供其他并发事务进行快照读。

Read View

关键字段

  • m_creator_trx_id：创建该 Read View 的事务 ID。
  • m_ids：创建 Read View 时其他未提交的活跃事务 ID 列表。不包括当前事务自己和已提交的事务（正在内存中）。
  • m_low_limit_id：创建 Read View 时最大的事务 ID+1，即下一个将要分配的事务 ID。大于等于这个 ID 的数据版本均不可见。
  • m_up_limit_id：活跃事务列表 m_ids 中最小的事务 ID，如果 m_ids 为空，则 m_low_limit_id 为 m_up_limit_id。小于这个 ID 的数据版本均可见。

Read View 可见性判断

  • DB_TRX_ID == m_creator_trx_id，表示当前事务访问自己修改的记录，因此该版本可以被当前事务访问
  • DB_TRX_ID < m_up_limit_id，表示该版本是在当前事务生成 ReadView 之间提交的，因此该版本可以被当前事务访问
  • DB_TRX_ID >= m_low_limit_id，表示该版本是在当前事务生成 ReadView 之后提交的，因此该版本不能被当前事务访问
  • DB_TRX_ID >= m_up_limit_id && DB_TRX_ID < m_low_limit_id && m_ids 包含 DB_TRX_ID，
    表示创建 ReadView 时生成该版本的事务仍处于活跃状态，因此该版本不能被访问
  • DB_TRX_ID >= m_up_limit_id && DB_TRX_ID < m_low_limit_id && m_ids 不包含 DB_TRX_ID，
    表示创建 ReadView 时生成该版本的事务已提交，因此该版本能访问

RC 和 RR 下的 Read View

  • RC：每次 SELECT 数据前都生成一个 ReadView
  • RR：只在第一次读取数据时生成一个 ReadView，后面会复用第一次生成的

案例

初始化

MYSQL 默认隔离级别为可重复读

场景一

编号 事务 A 事务 B
1 BEGIN;
2 select n from idn where id=1; BEGIN;
3 update idn set n=2 where id=1; select n from idn where id=1;
4 select n from idn where id=1; update idn set n=3 where id=1;
5 COMMIT;
6 select n from idn where id=1;
7 COMMIT;
  • 时间点 3 的时候，事务 A 将 id=1 的记录 n 设置为 2，对于事务 B 来说此时的 ReadView，事务 A 处于活跃中的事务，但是未提交，所以不可见，其查询结果仍是 1
  • 时间点 4 的时候，事务 B 会阻塞，因为事务 A 在时间点 3 执行了 update 语句，对 id=1 的记录上了行锁
  • 时间点 5 的时候，事务 A 提交了，释放了行锁，事务 B 的 update 语句成功执行，id=1 的记录 n 设置为了 3
  • 时间点 6 的时候，事务 B 查询 id=1 的记录，因为最新版本的所属事务就是自己，所以看到的结果 n=3

4 select n from idn where id=1; select n from idn where id=1;

6 select n from idn where id=1; select n from idn where id=1;
7 select n from idn where id=1 for update;
8 COMMIT; COMMIT;
  • 时间点 4 的时候，事务 B 查询 id=1 的记录，因为此时事务 A 处于活跃状态，因此事务 A 的修改，事务 B 不可见
  • 时间点 6 的时候，事务 B 查询 id=1 的记录，因为 mysql 的隔离级别设置为可重复读，所以 ReadView 在时间点 4 的时候已经生成，对于事务 A 的判断是处于活跃中的事务且未提交，所以不可见，查询的结果仍是 1
  • 时间点 6 的时候，事务 C 查询 id=1 的记录，此时生成对应的 ReadView，事务 A 已经提交属于历史版本小于事务 C 的 m_up_limit_id，可见，查询的结果 n=2
  • 时间点 7 的时候，事务 B 查询 id=1 的记录，但是加上了 for update 语句，上了排它锁，属于当前读，读取的是最新版本，查询的结果 n=2

场景三

编号 事务 A 事务 B
1 BEGIN;
2 select n from idn where id=1; BEGIN;
3 update idn set n=n+1 where id=1; select n from idn where id=1;
4 select n from idn where id=1; update idn set n=n+1 where id=1;
5 COMMIT;
6 select n from idn where id=1;
7 COMMIT;
  • 时间点 4 的时候，事务 B 会阻塞，因为事务 A 在时间点 3 执行了 update 语句，对 id=1 的记录上了行锁
  • 时间点 5 的时候，事务 A 提交了，释放了行锁，事务 B 的 update 语句成功执行，id=1 的记录 n=n+1，此时因为是 update 语句，所以是当前读，n 的初始值为事务 A 更新后的值 2，然后再加 1，最终等于 3
  • 时间点 6 的时候，事务 B 查询 id=1 的记录，因为最新版本的所属事务就是自己，所以看到的结果 n=3

什么是 oss？

全称是 Object Storage Service，直译就是对象存储服务。OSS 具有与平台无关的 RESTful API 接口，您可以在任何应用、任何时间、任何地点存储和访问任意类型的数据。

常见的 OSS 供应商

  • 国内：阿里云 OSS，腾讯云 OSS，七牛云 OSS
  • 国外 Amazon AWS，MinIO，其中 MinIO 是开源可以自建

oss 和文件系统的对比

对比项 OSS 文件系统
数据模型 OSS 是一个分布式的对象存储服务，提供的是一个 Key-Value 对形式的对象存储服务。 文件系统是一种典型的树状索引结构。
数据获取 根据 Object 的名称（Key）唯一的获取该 Object 的内容。虽然您可以使用类似 test1/test.jpg 的名称，但是这并不表示 Object 是保存在 test1 目录下。对于 OSS 来说，test1/test.jpg 仅仅只是一个字符串，与 example.jpg 并没有本质的区别。因此不同名称的 Object 之间的访问消耗的资源是类似的。 一个名为 test1/test.jpg 的文件，访问过程需要先访问到 test1 目录，然后再在该目录下查找名为 test.jpg 的文件。
优势 支持海量的用户并发访问。 支持文件的修改，例如修改指定偏移位置的内容、截断文件尾部等。也支持文件夹的操作，例如重命名目录、删除目录、移动目录等非常容易。
劣势 OSS 保存的 Object 不支持修改（追加写 Object 需要调用特定的接口，生成的 Object 也和正常上传的 Object 类型上有差别）。用户即使只需要修改一个字节也需要重新上传整个 Object。OSS 可以通过一些操作来模拟类似文件夹的功能，但是代价非常高。例如重命名目录，如果希望将 test1 目录重命名成 test2，则 OSS 的实际操作是将所有以 test1/开头的 Object 都重新复制成以 test2/开头的 Object，该操作会消耗大量的带宽、存储、计算、时间资源。因此在使用 OSS 时请尽量避免类似的操作。 受限于单个设备的性能。访问越深的目录消耗的资源也越大，操作拥有很多文件的目录也会非常慢。

什么是 bucket？

阿里云中的解释：在上传数据（例如文档、图片、音视频等）到 OSS 之前，您需要在 OSS 所支持的地域中创建一个存储空间（Bucket），然后将无限数量的对象（Object）上传到该 Bucket 中。

我的理解：根文件夹，且所有上传的文件都是平铺在根文件夹中，没有目录结构（实际上有伪目录的概念，是个空的文件，主要用于控制目录下文件的权限）

为什么需要本地文件表？

业务系统中只要有上传文件的功能，就有一定会有用户上传相同的文件名称的文件，此时如果使用本地存储或者 oss 存储，在同一个目录（bucket）下是无法存储相同名称的文件。
因此需要一张本地文件表，记录原始名称和存储名称的映射表。 此外，通过本地文件表，不仅可以统计各业务的文件数、空间消耗，还可以记录文件的 oss 配置，实现文件存储在不同的 oss 服务中。

数据直传至 OSS 是利用 OSS 的表单上传 PostObject 接口。通过客户端先调用应用服务器生成并返回 Post 签名和 Post Policy，再使用这些信息上传到 OSS 服务器。为了将文件信息回写到本地文件表，此时有两种选择：

  1. 如果 OSS 服务支持回调，则可以通过应用服务器返回对应的回调接口、以及指定回调的数据
  2. 如果 OSS 服务不支持回调，则由客户端在上传结束后发起回调，可以复用上述接口

各种线程泄露问题

发表于 2023-06-19 分类于 Java Valine：

常用排查手段

  • 通过监控工具观察 web 容器所在服务器的状态，一般看 cpu、内存、socket 连接数
  • 通过监控工具观察 jvm 状态，一般看堆内存、gc、io、线程池状态
  • jmap -dump:live,format=b,file=FILE PATH PID dump jvm 内存，观察线程信息和堆内存信息

2023-06-19

事件描述：UAT 环境，进去项目首页，出现部分接口卡死的现象，但是其他接口都能正常请求。

事件原因：dump jvm 内存后，发现都卡死在CompletableFurture#Join这个方法。通过 grafa 监控的线程池状态，当前线程数已经达到最大线程数，且队列中已经排队 2000 多个任务。观察 dump 文件中的线程栈信息，发现有 200 多个容器线程处于等待状态，卡死在CompletableFurture#Join这个方法，同时线程池中的线程也处于处于等待状态，卡死在CompletableFurture#Join这个方法。根据线程池的线程栈调用信息，发现都是在某个业务类的方法进来，该业务类方法也开启了线程调用。

根本原因：总结下来就是，使用了同一个线程池，开启线程异步执行任务 A，任务 A 中又开启了线程异步执行任务 B，在并发场景高的情况下，可能会出现线程池中得到线程执行的都是任务 A，所有的任务 A 都执行到开启线程执行任务 B的时间点，但是由于活跃线程都被任务 A 占用了，所以任务 B 都在线程池队列中等待，而任务 A 又都在等待任务 B 返回结果，最终导致线程得不到释放而耗尽

CAPA：

  1. 在同一个线程池中开启的线程在执行过程中不允许再开启该线程池中的其他线程去执行任务
  2. 在调用外部服务的时候，需要配置超时熔断机制，避免卡死后带来的雪崩

2023-01-28

事件描述：生产环境，首页白页，所有请求后端接口卡死

事件原因：通过 grafa 观察后端服务器状态，发现 socket 连接数搞到 8k，web 容器的线程数也达到 500 多，没有得到释放。

根本原因：dump jvm 内存后，发现线程栈信息，都卡死在CountDownLatch#await上，根据堆栈提示的类和代码行数，找到发现在使用多线程调用时，线程执行过程中抛出了运行时异常，countDown 方法没有放在 finally 中，得不到执行，且 await 方法没有设置超时时间，导致主线程一直阻塞在 await 方法，最终 web 容器的线程池耗尽而卡死。

CAPA：

  1. 所用用到闭锁的地方，都需要将释放锁的逻辑放到 finally 中，且 await 都需要设置超时时间
  2. 代码提交的时候用 sonarlint 扫描，避免这些 block 问题
  3. 配置 actuator 监控线程池的使用状况，配置预警和告警通知，及时发现线程池状态不健康等问题

2022-UN

事件描述：生产环境，首页白页，大部分请求后端接口卡死，过一段时间全部接口全部卡死

事件原因：通过 grafa 观察后端服务器状态，发现 socket 连接数搞到 8k，web 容器的线程数也达到 500 多，没有得到释放。

根本原因：微服务调用存在循环调用的问题。服务 A 调用服务 B，服务 B 又调用了服务 A。并发高时，循环调用导致了服务 A 的 web 容器线程数一下子上来，从而导致了服务 B 想要调用服务 A 得排队，继而导致服务 A 线程得不到释放，外部请求都在队列中排队，最终卡死。

CAPA：

  1. 微服务间避免循环调用，划清微服务的功能界限，只能单向调用
  2. 微服务请求一定要设置超时时间和熔断机制，避免雪崩
