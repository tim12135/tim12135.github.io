SaaS 多租户差异化表单设计方案总结

一、问题背景

在 SaaS 场景中，不同租户（客户）虽然共享同一套业务系统，但往往需要根据自身业务特点自定义表单字段。例如：

  • 租户 A 的 CRM 需要记录”客户行业分类”字段
  • 租户 B 的 CRM 需要记录”客户信用等级”字段
  • 租户 C 需要在标准字段基础上额外增加 20 个自定义字段

核心挑战在于：如何在共享底层数据结构的前提下，让每个租户拥有独立的字段配置（Field Definition）和数据存储（Field Value），同时保持查询性能、数据一致性和可维护性。

二、主流数据结构设计方案

方案一：EAV 模型（Entity-Attribute-Value）

数据结构

每条业务数据的一个自定义字段值占一行，通过 field_id 关联到字段定义。

优点

  • 架构简单直观，扩展性强，新增字段无需改表结构
  • 支持行级并发锁，不同字段更新互不干扰
  • 删除字段只需清理元数据 + 级联删除值行
  • 对关系型数据库友好，不依赖特定数据库特性

缺点

  • 查询一个实体的所有字段需要大量 JOIN 或多次查询，性能差
  • 无法利用数据库的类型约束，所有值以字符串存储
  • 复杂条件查询（多字段组合过滤）SQL 极其冗长且低效
  • 存储膨胀严重，每条数据的每个字段值都占独立行，标识符重复存储
  • 写入性能随索引数量增长而下降

适用场景

  • 自定义字段数量较少（< 50）
  • 传统成熟系统的局部字段扩展
  • 对查询性能要求不高的轻量级配置场景

方案二：JSON / JSONB 列存储

数据结构

所有自定义字段值打包成一个 JSON 存储在主表的一个列中，字段定义表仅作为元数据描述。

优点

  • 存储紧凑，一条数据一行，无冗余行
  • 读写性能好，一次 IO 即可获取全部字段
  • PostgreSQL 的 JSONB 支持 GIN 索引，可对 JSON 内部键值高效查询
  • 字段数量无上限，天然支持嵌套结构
  • 开发简单，ORM 友好

缺点

  • 行级锁导致并发更新同一记录的不同字段时产生写争用
  • 全局字段删除需要遍历所有行清理 JSON 中的对应键
  • 无法强制严格的数据类型约束（依赖应用层校验）
  • 深层嵌套查询复杂度随层级增长
  • 部分传统关系型数据库（如 MySQL 5.7 以下）JSON 支持有限

适用场景

  • 大多数可扩展的 SaaS 产品（推荐首选方案）
  • 字段数量多但单条数据并发更新不频繁
  • 使用 PostgreSQL / MongoDB 等对 JSON 原生支持好的数据库
  • 需要快速迭代的敏捷型产品

方案三：宽表模式（预留列 / Flex Columns）

数据结构

预先在主表中创建固定数量的预留列（如 val_00 ~ val_99），通过元数据表记录每个租户的字段映射到哪个预留列。Salesforce 即采用此方案的核心变体。

Salesforce 的实践

Salesforce 的多租户架构基于”Universal Data Dictionary (UDD)”：

  • 每条数据通过 OrgID 隔离租户
  • flex columns 以”canonical format”（规范字符串格式）存储所有类型数据
  • 运行时引擎根据 MT_Fields 的类型定义做类型转换
  • 通过大规模元数据缓存 + 按 OrgID 物理分区裁剪提升性能

Salesforce Flex Columns 技术细节

1. MT_Data 表的列类型与长度

字段类型：所有 Value 列均为变长字符串（VARCHAR / VARCHAR2）

  • 无论业务字段是数字、日期、文本还是布尔，底层统一存储为字符串
  • 数据库层面不区分类型，所有类型约束和校验在应用层完成
  • 每行的 501 个 Value 槽位对应 Salesforce 每个对象最多约 500 个自定义字段的限制

长度设定策略：

数据类型 存储方式 长度处理
文本（Text） 直接存入 Value 列 最长 255 字符存入 flex column
长文本（Long Text Area） 外置到 MT_Clobs 表 最长 32,000 字符，CLOB 存储
数字（Number） 转为规范字符串存入 Value 列 如 12345.67 → "12345.67"
日期/时间（Date/DateTime） 转为规范字符串存入 Value 列 如 2026-07-16 → "2026-07-16T00:00:00Z"
布尔（Checkbox） 转为字符串 "true" / "false"
选项列表（Picklist） 直接存入 Value 列 存储选项的 API Name 字符串
关系（Lookup/Master-Detail） 存储目标记录 ID 18 位或 15 位 ID 字符串

关键设计：长短分离

  • 短数据（≤ 255 字符）→ 存入 MT_Data 的 flex column（VARCHAR）
  • 长数据（> 255 字符，最长 32,000）→ 存入 MT_Clobs 表（CLOB 类型），主表只保留引用

MT_Clobs 表结构（一个记录有多个长文本字段怎么存？）：

MT_Clobs 采用与 MT_Indexes 相同的”一行一个字段值”模式。一条业务记录上有 N 个长文本字段，就在 MT_Clobs 中产生 N 行，通过 FieldID 区分：

  • 同一条记录（RecordID=1001）有 3 个长文本字段（FieldID=10/11/12），占 3 行
  • 每行只存一个 CLOB 值，通过 (OrgID, ObjectID, RecordID, FieldID) 四元组唯一定位
  • MT_Data 中对应的 Value 列存一个简短引用标记（如字段 ID 或 null），表示”该字段值在 MT_Clobs 中”

为什么不用一行存多个 CLOB 列？（如 ClobValue0 ~ ClobValueN）

方案 一行一个 CLOB（实际方案） 一行多个 CLOB 列
扩展性 无限，新增长文本字段无需改表 有上限，需预留列
行大小 每行只有一个 CLOB，行大小可控 多个 CLOB 堆在一行，行可能超大
更新性能 更新单个字段只锁一行 更新任一字段锁整行
存储效率 为空的 CLOB 不占行 空列仍占位
查询方式 按 FieldID 过滤 需知道列位置

这与 MT_Indexes 的设计思路完全一致：用行数换列数，牺牲少量 JOIN 性能换取无限扩展性。

3. MT_Fields 元数据表结构
  • FieldNum：核心映射字段，指定该自定义字段的数据存储在 MT_Data 的哪个 Value 槽位
  • 同一个 Object 下，每个租户的 FieldNum 独立编号（不同租户可复用同一个 Value 列）
  • DataType：记录原始业务类型，供运行时做类型转换
  • IsIndexed：标记该字段是否需要索引，决定是否同步写入 MT_Indexes
4. MT_Indexes 索引透视表

由于多个不同类型的业务字段共享同一个 VARCHAR Value 列，数据库原生索引无法有效工作。Salesforce 引入了 MT_Indexes 透视表：

RecordID 是最关键的列——它指向 MT_Data 中的 ObjectInstanceID，是连接索引与原始数据的桥梁。

为什么需要 MT_Indexes（核心问题解答）：

如果不加 MT_Indexes，在 MT_Data 上直接查询 WHERE Value1 > 5000000 面临两个致命问题：

  1. 类型错误：Value1 是 VARCHAR 列，存的 "5000000" 是字符串。字符串比较 "5000000" > "4999999" 的结果在数据库层面是不可靠的（字符串按字典序比较，"5000000" < "4999999" 为 true，因为字符 '5' > '4' 但长度不同会导致错乱）。更严重的是 "10000000" < "5000000" 在字符串比较下成立（因为 '1' < '5'），完全错误。

  2. 语义混淆：同一个 Value1 列，租户 A 存的是数字 revenue，租户 B 存的可能是文本 credit_level。如果直接在 Value1 上建索引，索引中混合了数字字符串和文本字符串，查询结果毫无意义。

MT_Indexes 通过以下设计解决了这两个问题：

  • 强类型列（NumValue/DateValue/StringValue）：让数据库以正确的数据类型做比较和索引
  • FieldID 过滤：确保只比较同一语义的字段值，不会跨租户、跨字段混淆
  • RecordID 回表：拿到匹配的 RecordID 后，回到 MT_Data 取完整记录

本质是”二级索引”模式：MT_Data 是堆表（主存储），MT_Indexes 是二级索引表。写入时同步写两处（主表 + 索引表），读取时先查索引表拿 ID，再回表取数据——这与数据库内部 B-Tree 二级索引的工作原理完全一致，只是 Salesforce 在应用层手动实现了它。

5. 整体数据读写流程

写入时：MT_Fields 决定数据写入哪个 Value 列、是否同步 MT_Indexes、是否外置 MT_Clobs
读取时：MT_Fields 决定从哪个 Value 列读取、用何种类型转换函数还原

6. 关键设计总结
设计点 方案 原因
列数据类型 统一 VARCHAR（变长字符串） 避免为每种业务类型建列，实现统一存储
列数量 501 个（Value0Value500） 平衡单行存储容量与字段扩展需求
短数据长度 ≤ 255 字符存入 flex column 控制 VARCHAR 列的物理存储大小
长数据长度 ≤ 32,000 字符存入 MT_Clobs 超长数据不撑大主行，外置 CLOB
类型处理 canonical format + 运行时转换 数据库不负责类型安全，应用层全权处理
索引策略 MT_Indexes 透视表 + 强类型列 解决 VARCHAR 列无法按原始类型索引的问题
元数据驱动 MT_Fields 的 FieldNum 映射 新增字段只需插元数据行，零 DDL
7. 查询引擎中间层（开发者怎么查 MT_Data？）

开发者绝不直接写 SQL 查 MT_Data。 Salesforce 在应用层和数据库之间构建了一个完整的运行时查询引擎，开发者只需写 SOQL（Salesforce Object Query Language），引擎自动完成从逻辑字段到物理列的翻译。

元数据缓存：引擎高效的关键

如果没有缓存，每次查询都要先查 MT_Fields 获取字段映射，再查 MT_Data 取数据——两次数据库往返。Salesforce 的解决方案：

  • 每个 App 节点维护一份分布式内存元数据缓存
  • 字段定义变更时，缓存自动失效并重新加载
  • 缓存命中率极高（字段定义变更频率远低于数据读写频率）
  • 效果：SOQL → SQL 翻译在内存中完成，零额外数据库查询
总结：三层架构职责划分

业务端绝不会自己拼接 SQL。 整个翻译过程由运行时引擎 black-box 完成——这就是 Salesforce “元数据驱动架构”的核心价值：开发者面对的是逻辑对象模型，引擎负责一切物理映射。

8. 联表查询（SOQL Relationship Queries）

支持，但方式和 SQL JOIN 完全不同。 SOQL 没有 INNER JOIN / LEFT JOIN 关键字，不支持任意表之间的自由关联。只能通过预定义的关系（Lookup / Master-Detail）进行导航式查询。

① 子查父（Child-to-Parent，向上导航）

② 父查子（Parent-to-Child，向下导航）

用子查询（嵌套 SELECT）获取子记录列表，最多 1 级：

等价 SQL 语义：Account LEFT JOIN Contact ON Contact.AccountId = Account.Id

常见 SQL JOIN 的 SOQL 等价写法
SQL JOIN 类型 SOQL 等价写法 示例
LEFT JOIN（父→子） 子查询 SELECT Name, (SELECT Name FROM Contacts) FROM Account
LEFT JOIN（子→父） 点号语法 SELECT Name, Account.Name FROM Contact
INNER JOIN（子→父） 点号 + WHERE 过滤 SELECT Name, Account.Name FROM Contact WHERE AccountId != null
INNER JOIN（父→子） 半连接子查询 SELECT Name FROM Account WHERE Id IN (SELECT AccountId FROM Contact)
LEFT ANTI JOIN NOT IN 子查询 SELECT Name FROM Account WHERE Id NOT IN (SELECT AccountId FROM Contact)
与 SQL JOIN 的核心差异
维度 SQL JOIN SOQL Relationship Query
关联条件 任意字段（ON A.col = B.col） 只能用预定义关系字段（Lookup / Master-Detail）
JOIN 关键字 INNER JOIN / LEFT JOIN / RIGHT JOIN 无关键字，用点号或子查询
任意表关联 支持（任意两表只要有逻辑关联即可 JOIN） 不支持（必须有预定义关系）
向上深度 无限制 最多 5 级
向下深度 无限制 最多 1 级子查询
多对多 通过中间表 JOIN 需通过 junction object 分两步查
聚合 + JOIN 自由组合 受限（子查询中不能有聚合）

关键点：Account 和 Contact 在物理层共享同一张 MT_Data 表，只是 ObjectID 不同。关系查询本质是 MT_Data 自连接（Self-Join）。

如果是父查子（带子查询），引擎翻译为不同的策略：

为什么父查子用两步而非一个 JOIN？

策略 一个 JOIN 两步查询（实际方案）
SQL 复杂度 一条复杂 SQL 两条简单 SQL
结果集 笛卡尔积（父行 × 子行），需应用层去重 父记录一组 + 子记录一组，天然分组
结果结构 扁平行（需要应用层组装成嵌套结构） 直接映射为嵌套 JSON
数据库压力 一条大 JOIN（自连接 + 可能的索引扫描） 两条简单查询（各走各自索引）
分页友好 难（子记录数膨胀导致分页不准） 易（父记录分页，子记录各自独立）

Salesforce 选择两步查询策略，因为 SOQL 的返回结构本身就是嵌套的（Account 里嵌套 Contacts 数组），两步查询的结果天然就是嵌套结构，无需应用层组装。

优点

  • 单行存储，读取性能优于 EAV
  • 规避了表结构变更（DDL）风险
  • 保持了关系型表结构，可做有限 SQL 查询
  • 适合大规模多租户 SaaS，Salesforce 已验证可行性

缺点

  • 预留列数量有上限，超出后需 DDL 扩列
  • 所有值以字符串存储，类型转换在应用层完成
  • SQL 查询能力受限，复杂查询需应用层拼装
  • 多租户共用列，索引策略复杂，不同租户的同一列语义不同
  • 开发成本极高，需要构建完整的元数据引擎和运行时
  • 数据库账号权限管理不当易引发跨租户数据越权

适用场景

  • 超大规模多租户 SaaS 平台（如 Salesforce 级别）
  • 垂直领域 SaaS，字段模式相对固定
  • 团队有强基础设施能力，可投入大量研发资源

方案四：动态 DDL（运行时修改表结构）

数据结构

每个租户有独立的表或独立的列，通过 DDL 在运行时动态创建/修改：

或采用每租户独立表（Table-per-Tenant）策略。

优点

  • 完全的关系型能力：类型约束、索引、复杂 SQL 查询全部原生支持
  • 数据一致性强，可利用外键、CHECK 约束
  • 对外部 BI 工具和报表系统友好
  • 无需额外的元数据引擎，直接读取数据库 Schema

缺点

  • 需要 DBA 级别权限，安全风险高
  • DDL 操作（ALTER TABLE）在高并发下可能引发锁表
  • 多数据库方言适配成本高（MySQL / PostgreSQL / Oracle DDL 语法不同）
  • 表数量随租户增长膨胀，元数据管理困难
  • 字段重命名 / 删除时数据迁移成本高
  • 不适合 Serverless / 云原生无状态部署

适用场景

  • ERP、MES 等企业级复杂系统（国内主流选择）
  • 租户数量有限且稳定的私有化部署场景
  • 对数据一致性和 SQL 查询能力要求极高的系统

方案五：混合方案（Hybrid）

实际生产中，成熟产品往往采用组合策略：

常见组合模式

组合 标准字段 自定义字段 代表产品
关系列 + JSON 固定列存储 JSON 列存储 大多数现代 SaaS
关系列 + EAV 固定列存储 EAV 行存储 传统企业系统
元数据引擎 + Flex Columns 元数据定义 flex 列存储 Salesforce
关系列 + 文档库 核心表存储 MongoDB 扩展 中大型 SaaS

典型实践：标准字段用关系列 + 自定义字段用 JSON

  • 标准字段享受关系型全部优势（索引、约束、查询优化）
  • 自定义字段享受 JSON 灵活性
  • 高频查询的自定义字段可通过表达式索引提升性能
  • 字段定义表驱动前端表单渲染和数据校验

  • 核心表：MT_Objects（对象定义）、MT_Fields（字段定义）、MT_Data（数据存储）
  • 关键设计：UDD 统一数据字典 + 元数据缓存 + 按 OrgID 物理分区裁剪
  • 亮点：将所有类型数据统一为 canonical format 字符串存储，运行时类型转换

Form.io

  • 方案：Schema-Driven（JSON Schema）
  • 核心设计：表单定义和提交数据均为 JSON 结构，分离存储
  • 多租户：通过资源定义、权限控制、认证隔离实现租户定制
  • 亮点：表单 JSON Schema 即是前端渲染蓝图，也是数据校验规则，做到”配置即代码”

钉钉宜搭 / 飞书低代码

  • 方案：模型驱动的混合方案
  • 核心设计：标准字段关系列 + 自定义字段扩展存储
  • 亮点：可视化表单设计器直接映射到后端数据模型，零代码创建租户专属表单

传统 ERP / MES

  • 方案：动态 DDL
  • 核心设计：每租户独立表结构，运行时 ALTER TABLE
  • 亮点：完全关系型能力，适合复杂业务约束场景

五、选型建议

按产品阶段选型

阶段 推荐方案 理由
MVP / 早期 JSON/JSONB 开发快、迭代灵活、PostgreSQL 原生支持
成长期 混合方案（标准列 + JSON） 兼顾性能与灵活性
成熟期 评估是否需要宽表/元数据引擎 当 JSON 性能瓶颈出现时演进

按业务特征选型

业务特征 推荐方案
字段数量 < 30，查询简单 JSON/JSONB
字段数量 > 100，需复杂查询 混合方案 + 表达式索引
需要 BI/报表对接 动态 DDL 或 混合方案（标准字段关系列）
超大规模 SaaS（万级租户） 宽表 + 元数据引擎
私有化部署、租户少 动态 DDL
需要嵌套/层级数据 JSON/JSONB

通用架构原则

  1. 元数据与数据分离：无论哪种存储方案，字段定义（元数据）必须独立于字段值（业务数据）
  2. 租户隔离优先：所有表必须带 tenant_id，所有查询必须强制过滤
  3. 标准 + 扩展分层：高频通用字段用关系列，低频定制字段用扩展存储
  4. 索引策略前置：在设计阶段就规划好哪些自定义字段需要索引，避免后期补救
  5. 数据校验在应用层：JSON / EAV / 宽表方案均无法依赖数据库做类型约束，需在应用层构建校验引擎

六、总结

没有”最好”的方案，只有”最合适”的方案。核心权衡轴是 灵活性 vs 性能 vs 复杂度：

  • 追求极致灵活 + 快速迭代 → JSON/JSONB（中小型 SaaS 首选）
  • 追求关系型能力 + 数据一致性 → 动态 DDL（企业级私有部署）
  • 追求超大规模 + 多租户隔离 → 宽表 + 元数据引擎（Salesforce 路线）
  • 追求平衡 → 混合方案（标准关系列 + JSON 扩展列，多数成熟 SaaS 的选择）
